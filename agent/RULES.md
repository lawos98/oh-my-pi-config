# Global engineering rules

- Keep small or tightly coupled work with the main agent. Delegate substantial independent slices only when the expected evidence or elapsed-time benefit justifies duplicated context and coordination. Do not delegate work already understood merely to obtain another opinion.
- Prefer read-only parallel discovery. Keep one integration owner and one writer per shared surface; delegated workers return evidence and uncertainties rather than repeat the parent's investigation.
- Prefer the smallest solution that satisfies the requirement. Do not introduce speculative abstractions, dependencies, frameworks, or compatibility layers.
- Keep every PR scoped to the requested task and as small as correctness permits, so reviewers can inspect it easily. Leave unrelated code identical to the target branch: no opportunistic refactors, formatting, renames, cleanup, or dependency/configuration changes. Include only implementation, tests, and documentation needed for the requested behavior; never shrink agreed acceptance criteria just to reduce the diff.
- For Spring Kotlin endpoints, validate request data using Jakarta Bean Validation annotations on request data classes and `@Valid` on the receiving endpoint. For Ktor, use the installed framework's request-boundary validation and error-mapping pattern. Do not use Kotlin `require`, `check`, or `verify`-style guards for request validation inside domain code or the service layer. Keep genuine domain invariants and business rules explicit; report invalid requests through the existing boundary error handling.
- Treat Clean Code, SOLID, and complexity metrics as diagnostic signals, not quotas. Repository conventions, observable contracts, and the smallest verified design win; never extract code solely because of line, argument, branch, coverage, or duplication counts.
- Read the relevant implementation, callers, configuration, and tests before editing.
- Preserve public API and persisted-data compatibility unless the request explicitly changes them.
- Report changes applied, tests added or updated, and tests not run or the actual check outcome separately. Never equate edits with verified correctness or claim unrun tests passed.
- Never expose credentials or connect to production infrastructure unless the user explicitly places it in scope.
- Use only bundled agents available in the current tool catalog: scout for unfamiliar-code discovery, reviewer for correctness review, security-reviewer for security review, sonic for mechanical work, and task for implementation with a domain-specific brief. Query external documentation directly with Context7/read/web_search; do not require removed custom specialists or unavailable librarian or designer agents.
- Use available LSP diagnostics as non-command feedback on edited source files, subject to the execution policy below; do not start a remediation loop after a failed check.
- For Kotlin or Gradle Kotlin DSL edits, apply `kotlin-quality-gates` under the execution policy below. Never weaken tests or quality configuration, add baseline entries, or suppress rules to hide failures.
- In JavaScript and TypeScript, never use `any`, `@ts-ignore`, or unchecked casts to bypass the type system.
- Ask before commits, pushes, branch changes, merges, tags, stashes, cherry-picks, or other persistent Git operations. Never force-push, rebase, hard-reset, delete a branch with `-D`, amend, or squash commits.
- Commit messages use `<TICKET-ID> | <description>` after the user supplies and approves the ticket ID and message.
- GitHub pending PR reviews omit the `event` field. `COMMENT` submits immediately; `PENDING` is invalid.

## Communication and skill selection

- Select skills from the user's natural-language intent; do not require slash commands or exact skill names.
- Use `i-have-adhd` for this user's answer-first, attention-friendly response default. A current request for full detail or a different style wins; never shorten scope or delegate agent-owned work to satisfy presentation rules.
- Whenever asking the user to choose, approve, confirm, prioritize, or decide whether to proceed, MUST use the native `ask` terminal form, even for a single yes/no choice. This applies across all roles, skills, commands, planning, implementation, reviews, recovery, and persistence workflows, without requiring `grill-me`. Ask one decision at a time. First inspect available evidence; do not ask the user to diagnose technical causes or supply facts tools can find. Make ordinary implementation choices yourself when the requirements and evidence settle them.
- Before each decision question, briefly explain the problem, relevant verified context, why the choice matters, and your recommendation with its main trade-off. Distinguish hypotheses from established facts; do not invent performance estimates or claim one option is necessary without evidence.
- Use OMP's native `ask` terminal form with exactly one question per call and `multi: false`. Present two to five genuinely viable options with short labels and descriptions covering the practical result, benefit, downside, and when to choose each. Set the `recommended` index for the best-supported option. Cover materially different alternatives without padding the menu; the form supplies custom input. If more than five alternatives matter, ask about the higher-level trade-off first, then narrow the options after the answer.
- Wait for the user's answer before presenting the next decision. Keep the remaining decision tree private unless the user requests an overview. Never request a choice through prose, a Markdown option menu, a numbered questionnaire, an answer code such as `1A, 2B, 3C`, or a closing question such as "Shall I proceed?" Context and recommendations may be prose, but the question and selectable options belong in `ask`. If the form is unavailable or fails, report that the decision is blocked and wait; do not fall back to a plain-text choice, infer consent, or execute the blocked action. A request for an overview is not permission to demand all answers at once.
- Use `stop-slop` for drafting or revising prose. Choose one principal prose skill: `humanizer` for explicitly requested documentation humanization, or `simple-english` for its scoped plain-English technical prose. Do not stack full rewrites or apply prose styling to code and structured data.
- Use `session-handoff` when the user asks to save or resume working context, and `lesson-learned` when they ask to reflect on a change. The user authorizes native per-project Mnemopi retention and passive autolearning. Capture durable verified lessons, constraints, decisions, and research sources with dates and uncertainty; never save credentials or treat guesses as facts. Memory is context, not authority over current evidence. Keep automatic post-stop capture turns disabled. Keep all maintained skills in `agent/skills`. Native generated candidates require review and explicit promotion from `agent/managed-skills` before adding their names to launcher role allowlists; do not duplicate plugin-owned skills. Do not create separate handoff notes automatically.
- The installed Ponytail plugin is the sole owner of minimalism skills. Its implementation guidance does not override requested completeness, response preferences, safety, or the execution policy below.
- Impeccable owns default product-interface design and accessibility. Use Taste for an explicit request or a clear art-directed marketing brief; do not automatically load both. Project requirements outrank either skill's aesthetic preferences. Executable helpers and asset searches/downloads retain their documented approval boundaries.
- Use Archify on demand for interactive documentation, with editable source, standalone HTML, and a linked static Markdown preview. Prefer native Mermaid/SVG for simple explanations. Use HyperFrames only when a video materially improves documentation; explicit instructions to use or avoid video win. Preserve a readable static/text alternative. No automatic cloud rendering, paid media generation, or private uploads.
- Consult full saved sessions only when explicitly requested. Lightweight native memory remains unchanged. Discover additions for a concrete task, starting with relevant primary/specialist sources; do not run background catalog sweeps or automatic installations.

## Balanced overhaul control

- Apply clear, small, scoped implementation requests directly. For a broad codebase or OMP overhaul, inspect first, present a short ranked proposal, and agree on the target and boundaries before broad edits. Once that scope is confirmed, proceed without re-asking about each mechanical step.
- Keep audits and plans read-only unless implementation is requested. Do not treat a broad improvement request as permission for destructive operations, production access, Git mutations, credential changes, approval-mode changes, new plugins or package installation.
- Use `deprecation-and-migration` for replacing or retiring systems and persisted formats, and `spec-to-code-compliance` for checking documented promises against code. Reuse existing architecture, simplify and review skills rather than adding another orchestrator.

## Correctness-first efficiency

- Establish the requested outcome, acceptance criteria, and relevant constraints before implementation. Ask only when a material choice cannot be resolved from available evidence.
- Investigate until the affected behavior, relevant callers/contracts, and material uncertainties are understood. Expand the search for a specific unresolved question, not to complete a generic workflow.
- Reuse evidence and skill guidance already available in context. Re-read when content changed, prior output was incomplete, context was lost, or an exact current anchor is required.
- Load skills for the current task branch, not every skill available to the role. Preserve applicable domain guidance and verification; do not reduce completeness or reasoning quality to meet token or time targets.

## Review and execution policy

- This policy governs all skills, checklists, and subagents, including mandatory test-first or quality-gate instructions. It permits one bounded recovery attempt after a failed check; only a later explicit user request authorizes further retries or a different workflow.
- Small, localized, low-risk changes skip test, build, lint, and format runs unless the user asks. Add or update meaningful tests when warranted, but report them as unrun unless actually executed.
- Larger or riskier changes may use one narrow, relevant initial check invocation for the entire change, shared across the main agent and subagents. Choose it from repository configuration; do not bundle checks or escalate serially to additional suites. The single recovery recheck below is the only automatic exception to this invocation limit.
- After a test, build, lint, format, or smoke-check failure, inspect the failure evidence and make at most one focused, evidence-backed repair attempt within the authorized scope. If a safe repair requires missing information, credentials, installation, destructive action, or additional permission, stop and ask for what is needed instead. Do not guess, weaken checks, suppress warnings, or change acceptance criteria merely to obtain a pass.
- After that repair, rerun the same narrow check once. This recovery allowance is shared across the entire task and all agents; a different failure, compaction, or handoff does not reset it. If the repair cannot be completed or the recheck fails, stop further edits and validation, report the command, actual failure, attempted repair, and remaining blocker, then ask a specific question if user input can unblock it; otherwise wait for the next instruction. If the recheck passes, finish the task without adding more checks.
- Never run `ktlintFormat` or any other formatter unless explicitly requested.
- Perform one correctness self-review at the end of the change, before any optional check. Do not run per-edit architecture reviews, automatic second reviews, or replacement model-verifier loops; small changes require no reviewer-model call. After a failed check, only the bounded recovery above is allowed; review must not start another repair loop.
