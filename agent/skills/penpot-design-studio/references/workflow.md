# Native design workflow

## Brief and reference selection

Establish the user task, audience, entry point, primary action, content, success state and likely interruption/failure. Use the current documents first. Ask only for material missing choices; keep independent work moving.

Select references for a named quality: information hierarchy, input behavior, navigation, art treatment, density or motion. Annotate what to borrow and what to avoid. Do not copy a whole visual identity or use impressive images as a substitute for interaction design. Consult the local template catalog for reusable native components and structural examples.

## Visual alternatives

Respect the requested count and the existing comparison plan. If none exists, propose a small set with genuinely different visual hypotheses before generating a large catalog. Keep task, copy, fixture data, state and frame size identical across comparisons. Vary composition, typography role, framing, density or art treatment deliberately; avoid producing only recolors.

Name each direction and explain the intended experience and tradeoff. Use a shared core of behavior and semantics while allowing meaningful visual differences. Include everyday UI alongside the expressive hero/game surface so decoration cannot hide practical problems. Do not select a winner on the user's behalf when founder acceptance is required.

## Components and tokens

Inspect native libraries before adding new ones. Use semantic roles for surfaces, text, borders, actions, focus, pending/success/error and disabled states. Map dark/light themes intentionally. Avoid copying raw palette literals into every object when the current API supports tokens/styles.

Create main components and instances for repeated contracts. Use variants for actual state/size/kind differences, not unrelated screens. Include applicable pressed, focus, disabled, busy, selected, validation and error examples. Use meaningful names, text styles, flex/grid behavior and constraints rather than a flat pile of disconnected rectangles.

Keep layer text editable; artwork is a separate asset. Import licensed templates into a separate reference file/page, inspect their dependencies and fonts, then adapt the useful component structure. Preserve required author notices and record changes when copying components into the product file. Do not claim a downloaded template was imported or verified unless it was.

## Prototype

Connect the requested journey with explicit starting points, controls, overlays and returns. Include material pending, empty, recoverable failure, unknown-result, interruption and reduced-motion branches. Use realistic fictional copy and content length. Show keyboard and safe-area constraints where they affect the task. Do not infer native functionality from Penpot preview alone.

If a native API cannot express an interaction, use supported prototype controls or label storyboard states clearly. Do not invent a working interaction, provider approval, backend, or performance result.

## Editing discipline and handoff

Inspect active IDs immediately before each batch, preserve unrelated user work and avoid concurrent writers. Checkpoint before changes; prefer supported native export/snapshot tools. Verify saved structure and a rendered export, then exercise available preview links.

Return the requested native `.penpot` snapshot with required libraries, live file link, page/board IDs, selected/proposed status, source requirement references, relevant screenshots and a short list of verification limits. Screenshots are supporting evidence, not the editable source. Keep source and attribution records with copied assets.
